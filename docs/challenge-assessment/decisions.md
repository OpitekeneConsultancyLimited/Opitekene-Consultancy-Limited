# Decisions log: Challenge an Assessment

Where the brief was ambiguous or clashed with the existing code, this log records the safer option taken, and why.

| ID | Decision | Why |
|---|---|---|
| D-01 | Branch `feature/challenge-assessment` is built on PR #10 (`front-page-sample`), not on `main`. | PR #10 is the owner's latest explicit design for the signed-out page and already removes the duplicated landing sections. Building on `main` would bring the duplicates back, or conflict with PR #10. **Merge PR #10 first.** |
| D-02 | The brief's `#lp-features` and `#lp-how` no longer exist (PR #10). Challenge an Assessment is advertised in the front page's services card and its "Sign in for the full TaxComp toolkit" list instead. | Keeps the owner's design. Nothing links to the removed ids. |
| D-03 | New Worker code is strict **TypeScript** in `worker/challenge/*.ts`. Existing `.mjs` files are unchanged. Only erasable TypeScript syntax is used (no `enum`, `namespace` or parameter properties), so Node 22 runs it directly in tests and wrangler (esbuild) bundles it with no build step. `tsc --noEmit` runs in CI (TypeScript 5.9.3, pinned). | Meets the strict-TypeScript rule without rewriting working JavaScript, and without a build step for the Pages site. |
| D-04 | Browsers never query Postgres. Every Challenge request goes through the Worker, which verifies the Supabase JWT and filters by `owner_user_id` (or by the assigned reviewer). RLS is on for every new table with the Worker-only policy, and `anon` / `authenticated` get **no grants**. | Same model as every existing table, which the production audit confirmed. It is narrower than per-user RLS policies: the public API cannot reach the data at all. Cross-user tests go through the Worker API. |
| D-05 | Documents go in a new private bucket, `assessment-documents`, under `<owner_user_id>/<case_id>/<document_id>`. **No client storage policies**, so browsers cannot reach any folder directly. Downloads stream through the Worker after an owner or reviewer check, instead of using signed URLs. | Stricter than per-folder policies. No URL can be shared or replayed after access is withdrawn. Matches `phase6-documents`. |
| D-06 | Assessment reading: (1) Claude `claude-opus-5-5` with `output_config.format` (JSON schema) for PDFs, photos and text; (2) Gemini (`GEMINI_API_KEY`, the existing model list) with a response schema; (3) a deterministic text reader for pasted text and text-based Word files. Every result passes the same validator. Invalid output fails cleanly and is never shown raw. | The brief's fallback pattern, plus a reader that costs nothing when no AI key works, which is the case in production today. |
| D-07 | Word (.docx) text is read in the browser with the built-in `DecompressionStream`; no library. Old binary .doc files are refused with a message asking for PDF or a photo. | No new dependency. Claude cannot read .docx directly. |
| D-08 | Pack tiers: `free` (explanation, deadline, checklist) for every signed-in user. `self-service` (full pack) for any active paid plan; a new `billing_plans.challenge_tier` column sets this to `self-service` for both existing plans. `reviewed` and `managed` are granted per case by staff in `challenge_case_entitlements`, after a manual or Flutterwave payment. **Gap:** the existing plans cannot sell a reviewed pack or a managed dispute; the owner must decide prices. | The brief allows "add an entitlement flag and record the gap". No new checkout is built. |
| D-09 | Reviewers are listed in `challenge_reviewers` (Supabase user id plus email), maintained by the owner with SQL. A case that needs review is assigned to the active reviewer with the fewest open cases, and a reviewer sees only cases assigned to them. | Reviewer access is enforced on the server. No reviewer ids are known, so none are seeded (Checkpoint B). |
| D-10 | A reviewer may enter verified statute text and may approve a rule set from the reviewer screen; both are written to the audit log. Code and seed data **never** set `approved_for_computation = true`. | Checkpoint C. Approval is a human action. |
| D-11 | The case ingestion script is JavaScript (`scripts/ulii-ingest.mjs`), not Python. | Same language as the rest of the tooling. `pyright --strict` therefore does not apply. |
| D-12 | No ESLint or Prettier is added. `tsc --strict --noEmit` covers the new TypeScript. | The project has never used a linter. Adding one to 70+ existing files would rewrite working code, which the brief forbids. |
| D-13 | DOCX packs are built in the browser by a small in-repo writer (an uncompressed ZIP with WordprocessingML). PDF comes from print CSS (Print, then Save as PDF). | No new dependency, and no document leaves the browser for conversion. |
| D-14 | Penal tax and interest are recomputed only from formula data in `law_provision_versions.computation_json`. All formulas are seeded with `rate: null` and `TODO_VERIFY`. Until a reviewer enters and approves a rate, the arithmetic check uses the rate printed on URA's own notice, labelled "using the rate shown on URA's notice; provisional". | Rates must not be invented. URA's stated rate lets an arithmetic error be shown without asserting the law. |
| D-15 | The day-counting conventions are flags in the rule data: `exclude_trigger_day = true` and `weekend_holiday_rule = "calendar"`, both marked `TODO_VERIFY`. The professional view shows them. | Brief, Section 7. |
| D-16 | The figures in the 2026 amendment seeds (assent and commencement dates) come from the owner's brief. They are seeded with `verification_status = 'pending-review'` and a note naming the brief as their source. | The dates are not invented, but they still need checking against the Gazette. |
| D-17 | Late-objection requests, deadlines after lapse, procedural issues, TAT preparation, low-confidence fields and disputed principal above UGX 50,000,000 (`CHALLENGE_REVIEW_THRESHOLD_UGX`, default `50000000`) all set `review_required`. | Brief, Section 8.3. |
| D-19 | The server code for Phases 1–4 (migration, API, reader, deadline engine, law register, classifier) is one commit, not four. | The API module imports all of them; per-phase commits would leave states that do not compile. The site (UI) work is committed separately. |
| D-20 | New TypeScript files use `.mts`. | The package is CommonJS (the existing tests rely on it); `.mts` makes Node and TypeScript treat the new files as ES modules without changing the package type. |
| D-18 | The theme colour mismatch (`manifest.webmanifest` `#176345` versus the page's `#0a1f3c`) is recorded, not changed. | Outside this task. |
